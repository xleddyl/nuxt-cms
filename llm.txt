# nuxt-cms: LLM guide

Nuxt module embedding a CMS in the app's Nitro server. Content types are declared in code (`cms.config.ts`); DB schema, migrations, TypeScript types and a read-only GraphQL API are generated from it. Admin panel at `/cms`. This guide covers: defining the data schema, and querying content from the app.

## 1. Setup (nuxt.config.ts)

```ts
export default defineNuxtConfig({
   modules: ['@xleddyl/nuxt-cms'],
   cms: {
      i18n: { locales: ['en', 'it'], defaultLocale: 'en' }, // only needed if using translatable fields
   },
})
```

The whole `cms` key is optional. `database` defaults to `{ driver: 'sqlite', path: 'data/cms.db' }`; switch to `{ driver: 'postgres', url, poolMax }`, `{ driver: 'libsql', url, authToken }` (Turso/remote, or omit `url` for a local file) or `{ driver: 'd1', binding }` (Cloudflare Workers, binding defaults to `DB`); each driver only accepts its own keys (`path` on sqlite, `url`/`authToken` on postgres/libsql, `poolMax` on postgres, `binding` on d1), plus `migrateOnBoot` (default true) on all of them. Install only the client for the driver you use: `pg` for postgres, `@libsql/client` for libsql; sqlite and d1 need nothing extra. Admin credentials come from `NUXT_CMS_ADMIN_EMAIL` / `NUXT_CMS_ADMIN_PASSWORD` env vars. Admin branding: `admin: { title, subtitle, logo }` replaces `nuxt-cms` / `Content studio` (empty `subtitle` hides it) and the default mark in the sidebar, mobile bar and login page; `logo` is a URL or root-relative public path (`/logo.png`, rendered as `<img>`), a path to an `.svg` file in the project (root-relative or `~/`, `@/`, `~~/`, `@@/`, inlined at build with scripts, `foreignObject`, `on*` attributes and fixed width/height stripped, so `currentColor` follows the theme) or raw `<svg` markup; a missing file or a non-svg project file fails the build (put raster images in `public/`). Media is configured under `cms.media` or `NUXT_CMS_MEDIA_*` env vars: `storage: 's3'` (default) uses S3-compatible object storage (`endpoint`, `region`, `bucket`, `accessKeyId`, `secretAccessKey`, `publicBaseUrl`, `presignExpiry`, `maxFileSize` in bytes, default 10485760); in `'s3'` mode folders can be created and deleted from the panel (an empty folder is kept alive by a `<folder>/.keep` object); `storage: 'local'` makes the media library read-only (no uploads/edits/deletes, listing only), only accepts `publicBaseUrl` (required), serving files from it instead of a bucket. With a root-relative `publicBaseUrl` (e.g. `/images` → `public/images`) the library is read from that folder (media keys are the paths relative to it): live from disk with a 1s cache wherever the folder exists, otherwise from a manifest baked at build time (the serverless case, where `public/` is not on the function's filesystem, so new files show up after you commit and deploy). Nothing is ever written back: `cms_media` only stores alt texts, so dev and production can safely share one database. `storage: 'filesystem'` writes uploads to a directory on the server's disk (`dir`, default `data/media`, or `NUXT_CMS_MEDIA_DIR`), serves them under a root-relative `publicBaseUrl` (default `/media`) and accepts `maxFileSize`; it needs a persistent disk. The media detail drawer has a Download button for the original file in every storage mode, served by the admin route `GET /api/cms/admin/media/download?key=` (`attachment` disposition; `s3` redirects to a presigned GET, `filesystem` and `local` stream from disk, `local` without the folder on disk fetches `publicBaseUrl` and streams). The admin client checks the upload size against `NUXT_PUBLIC_CMS_MEDIA_MAX_FILE_SIZE`, so a runtime override must set it and `NUXT_CMS_MEDIA_MAX_FILE_SIZE` to the same value. Remote DB credentials (postgres/libsql) can be overridden at runtime with `NUXT_CMS_DATABASE_URL` / `NUXT_CMS_DATABASE_AUTH_TOKEN` (libsql only).

Other top-level keys: `enabled` (or `NUXT_CMS_ENABLED=0`) turns the CMS off while the module stays in `modules[]`: the query composables become stubs that return their empty default without a request, and the generated types stay. `graphql: { maxDepth }` (default 8) caps query depth. `preview: { path, component }` sets the visual editor preview route (default `/cms/preview`) and the default preview wrapper of content entries (see Content). `admin.title`, `admin.subtitle` and `admin.logo` are build-time only (no env var).

## 2. Schema definition (cms.config.ts, project root)

```ts
import { defineCmsConfig } from '#nuxt-cms'

export default defineCmsConfig({
   <entryKey>: {
      id: '<entryKey>',            // must equal the object key
      label: 'Human label',
      kind: 'collection' | 'single' | 'page' | 'content',
      titleField: 'name',          // collections: entry title in admin; text, slug, email, number, date, datetime or single select
      drafts: true,                // optional; adds draft/published status (GraphQL returns published only)
      fields: { <fieldKey>: <FieldInput>, ... },
   },
})
```

- `collection` = many rows (list + detail queries). `single` = one document (single query). `page` = one row per route of the app (see Pages below). `content` = one content type (news, blog) whose items have system fields and a body of blocks, with drafts and scheduling (see Content below).
- `id`, `createdAt` (collections only), `updatedAt` are automatic: never declare them as fields.

### Field types

Every field has `label: string` and optional `required?: boolean` and `private?: boolean`. Type-specific options:

| type       | extra options                                                                      | stored/queried as |
| ---------- | ---------------------------------------------------------------------------------- | ----------------- |
| `text`     | `textarea?: boolean`, `translatable?: boolean`                                      | String            |
| `richtext` | `translatable?: boolean`                                                            | String (HTML)     |
| `number`   | `integer?: boolean`                                                                 | Float / Int       |
| `boolean`  | none                                                                               | Boolean           |
| `date`     | none                                                                               | String `yyyy-mm-dd` |
| `datetime` | none                                                                                | String, ISO 8601 UTC |
| `email`    | none                                                                               | String            |
| `slug`     | `from: '<fieldKey>'` (required; auto-generated from that text field)                | String            |
| `select`   | `options: string[]` (required)                                                      | String (enum)     |
| `json`     | none                                                                               | JSON              |
| `media`    | `mediaType?: T \| T[]` where `T` is `'image' \| 'video' \| 'file'`, `accept?: string[]`, `translatable?: boolean`, `mobile?: boolean` | CmsMedia object   |
| `relation` | `to: '<entryKey>'` (required), `cardinality?: 'many-to-one' (default) \| 'one-to-one' \| 'many-to-many'`, `onDelete?: 'set null' \| 'cascade' \| 'restrict'` | related entry / list |
| `blocks`   | `blocks: Record<name, { label, fields, component?, icon?, description? }>` (required) | array of typed blocks |

Notes:
- `mediaType` restricts the picker and the upload accept list to one kind of file, or to several when given a list (`['image', 'video']` for a slot that takes a photo or a video, with a filter pill per type). Omitted, or `'file'` anywhere in it, means any file. `CmsMedia.type` tells the app what was actually picked (`image` / `video` / `file`), so one slot can render an `<img>` or a `<video>`; `width`/`height` are filled for PNG, JPEG, WebP and GIF images and for MP4, M4V, MOV, WebM and MKV videos.
- `mobile: true` on a top-level `media` field adds an optional `<field>Mobile` media field (same `mediaType`, `accept`, `tab`, `translatable`, label `<label> (mobile)`) right after it, for a small-screen variant. The frontend picks the breakpoint and falls back to the main media. Not allowed inside `blocks`; a declared `<field>Mobile` key is a config error.
- `translatable` only works on `text`, `richtext` and `media`; requires `cms.i18n` locales. Stored per locale, resolved to a single value at query time via the `locale` argument (falls back to the default locale, then to any locale that has a value). Translatable `media` keeps the `CmsMedia` shape, so `cover { url alt }` is unchanged. Works inside `blocks` too, with the same query shape and no migration (the per-locale map lives in the block's JSON; blocks still holding a plain value are read as the default locale).
- `private: true` keeps a field out of the public GraphQL API: the column and the admin editor stay, but the field is absent from the entry type, the filters input, the sort enum, introspection and the generated `#cms-types`. Read those values server-side from the DB (`#cms-db` + `#cms-tables`), where they hold the raw column value (a media field holds the object key string). Use it when a value must only be served through your own authenticated route. Not allowed inside `blocks`: mark the whole `blocks` field private instead.
- `datetime` stores an instant as an ISO 8601 UTC string (`2026-05-01T08:30:00.000Z`). Input needs a time zone (`Z` or `+02:00`) and is stored in UTC; the admin picker uses the browser's time zone. Filters and sorts as a StringFilter.
- Block fields accept every type above except `slug`, `relation`, `blocks`, multi-select, and `private`. The admin edits a blocks field as a grid of tiles (preview, drag to reorder, click to open one block); when every block of the field has a `component`, an "Open visual editor" button also edits it in the visual editor (Block panel only, changes go back to the form). Any block item can carry `hidden: true` (block editor: Hide/Show): it dims the tile and, unless the block declares its own `hidden` field, drops the item from the public API.
- A block may name the site component that renders it: `component: 'SectionHero'` (or `'section-hero'`), plus `icon` (Heroicons outline) and `description` for the admin. Valid in every `blocks` field. The build fails when the component is not registered in Nuxt. Fields named `key`, `ref`, `class`, `style` are refused on a block with a component. `defineCmsBlocks({ ... })` from `#nuxt-cms` returns a block set unchanged (literal types kept) so several entries can share it. They may be `translatable`; the admin shows one locale switcher on the `blocks` field that drives every translatable sub-field.
- `tabs: [{ id, label }]` on an entry splits its admin form into horizontal tabs; `tab: '<id>'` on a field picks one. Admin-only: schema, column and query shape are unchanged. A field with no `tab` goes to the first tab; an entry with no `tabs` renders one plain form. An unknown tab id, a duplicate id or a tab with no label fails the build. Not allowed inside `blocks`. A failed save opens the tab holding the first invalid field.
- Login lockout: 5 failed logins from one IP, or for one email, return `429` for 5 minutes. Counters live in Nitro storage `cms:login-rate` (in-memory by default, so per instance). A successful login clears them.
- Media usage: each media tile and row shows how many entries use the file (or "unused"); deleting a used file or a folder shows the entries that use it first.
- Admin accounts: the env credentials (`NUXT_CMS_ADMIN_EMAIL`/`NUXT_CMS_ADMIN_PASSWORD`) sign in as the super admin, who is not stored in the DB and is the only one who can create, reset and delete other accounts (Settings → Users). Other accounts live in the `cms_users` table (scrypt hashes), have the `admin` role and can do everything else. First sign-in offers an optional password change; Settings → Account changes name and password. `cms_users` is a reserved entry name.
- Admin search: the sidebar search (⌘K / Ctrl K) matches config labels (entries, pages and paths, tabs, fields, blocks) and every stored text value (text, richtext without markup, slug, email, select, json, block fields, page field rows, media alt texts) in all locales, private fields included. It is served by `GET /api/cms/search?q=` (admin session required, 2 to 200 characters, case-insensitive LIKE with `%` and `_` escaped, 10 rows per entry, 50 value hits). A hit opens the editor with `?field=<key>&locale=<code>&block=<index>`, which switches to the tab, locale and block of the field, scrolls to it and highlights it. Admin-only: nothing is added to the public API.
- `layout` on an entry arranges the admin form: `[row, ...]`, where a row is a field key or an array of up to 4 keys side by side, and `{ title, description?, collapsed?, rows }` is a titled section. Unnamed fields go at the end. Admin-only. Unknown or repeated keys and rows over 4 fields fail the build. `list: { columns }` (collections) sets the default table columns (`status` allowed with `drafts`). `icon` (entry) sets the sidebar icon (Heroicons outline name). `description` and `placeholder` on a field add a help text and an input placeholder. Admins can override columns and layout in Settings; the override is stored in the `cms_settings` table and `settings`/`cms_settings` are reserved entry names.
- `showIf: { field, eq }` / `{ field, in: [...] }` (array = AND) hides a field in the admin until another field of the entry matches. Admin-only: schema, column and query shape are unchanged. A hidden field keeps its stored value. On a conditional field `required` means "required while visible": enforced by the admin form only, so the column stays nullable and the GraphQL field optional (two opposite branches can never both be filled). It can target `select`, `boolean`, `text`, `number`, `date`, `email`, `slug` (not blocks/relation/media/json/multi-select/translatable), and values are checked against a target select's `options` at build time. Not allowed on the `titleField` nor inside `blocks`.
- After changing the schema, restart dev (migrations are generated + applied on boot).
- Migrations live in `server/db/migrations/<driver>` and must be committed. They are inlined into the server bundle at build time (no filesystem access at runtime), which is what makes serverless hosts work; `migrateOnBoot: false` / `NUXT_CMS_MIGRATE_ON_BOOT=false` defers them to CI. D1 has no transactions and applies migrations on the first request instead of at boot.

### Pages

`kind: 'page'` holds the content of the pages of the app: one row per route, one admin section.

```ts
pages: {
   id: 'pages', label: 'Pages', kind: 'page',
   routes: 'auto',                 // default: one row per page file; or an explicit list of paths
   include: ['/extra'], exclude: ['/cms'],
   order: ['/', '/about'], labels: { '/': 'Home' },
   fields: { title: { label: 'Title', type: 'text', translatable: true } },   // every page
   overrides: { '/about': { intro: { label: 'Intro', type: 'text' } } },      // one path only
}
```

- `routes: 'auto'` reads the page files: dynamic routes are skipped, route groups leave the path.
- An override adds fields to one path; `null` removes a shared field from that path (`overrides: { '/': { gallery: null } }`). It may not redeclare a shared field, and two paths declaring the same field name must use the same type.
- `path` is reserved and unique; the row id comes from the path (`/a-b/c` gives `aBC`, `/` gives `home`).
- One page entry per config; no `titleField`, no `drafts`, no delete from the admin.
- Storage: the page table holds `id`, `path`, `updated_at` and the fields listed in `columns: ['metaTitle', ...]` (optional, each must exist on every page); every other value is a row of `<entry>_fields` (`page_id`, `key`, `position`, `value`) or `<entry>_media` (`page_id`, `key`, `position`, `media_key`). Block values are rows keyed `<field>.<subfield>` per `position`, plus `<field>._type`. Relations and slugs must be in `columns`; many-to-many is not supported. GraphQL, types, queries and admin see one flat object per page. Upgrading from 0.1.56 or earlier is breaking: the generated migration drops the old page columns, so add a hand-written data copy between its CREATE TABLEs and DROPs (see docs/schema.md).
- Saving a page rejects (400) media keys that are not in the media library.
- In the admin the pages are a tree that follows the routes, and the editor title is a breadcrumb.
- Queries: `<entry>(locale)` for the list, `<entry>ByPath(path, locale)` for one page.
- A script that loads `cms.config.ts` by itself gets no routes: fill them with `resolveCmsPages(config, { root?, pagesDir? })` from `@xleddyl/nuxt-cms/seed`.

### Content

`kind: 'content'` is one content type (news, blog, ...); declare one entry per type.

```ts
const sections = defineCmsBlocks({ text: { label: 'Text', component: 'SectionText', fields: { ... } } })

news: {
   id: 'news', label: 'News', kind: 'content', icon: 'newspaper',
   blocks: sections,                                                        // required: body blocks
   fields: { category: { label: 'Category', type: 'relation', to: 'categories' } }, // optional extras
   labels: { excerpt: 'Summary' },                                          // optional system labels
   tabs, layout, list,                                                      // as on collections
   preview: { component: 'NewsArticle' },                                   // optional preview wrapper
}
```

- System fields, injected (declaring one is a config error): `title` (text, translatable, required, the titleField), `slug` (unique, required, generated from the title in the default locale), `publishedAt` (datetime), `excerpt` (textarea, translatable), `cover` (media image), `body` (blocks from `blocks`), `seoTitle`, `seoDescription` (translatable), `seoImage` (media image). Text fields are translatable only when `cms.i18n.locales` is set.
- Always has draft/published `status`, `createdAt`, `updatedAt`. `titleField`, `drafts`, `columns`, `routes`, `overrides` and a custom `table` are config errors. Default list columns: title, status, publishedAt.
- Public API: only `status = published` and `publishedAt <= now`. Drafts and scheduled items (published with a future date) are invisible to list, count, byId, bySlug and relations. Publishing with an empty `publishedAt` sets it to now.
- Relations may target a content entry (`to: 'news'`).
- Admin: sidebar group Content; list badge "Scheduled" for future items; items open in the visual editor (`/cms/<entry>/new`, `/cms/<entry>/<id>`): top bar (back, title, status, locale switch, desktop/mobile width, Schedule, Save, Publish/Unpublish, Delete), center iframe of the site preview page with live updates, right inspector with tabs Content (system and extra fields, ordered by `layout`), Block (selected block form, or block list plus palette) and SEO. In the canvas: hover outline with label, click to select, drag handle and arrow keys to reorder, `+` between blocks opens the palette (label, icon, description), Duplicate, Hide, Delete. In the block list, Alt+ArrowUp/Down moves a block. Save validates and opens the tab/block of the first error.
- `preview: { component }` (content entries only; `cms.preview.component` in nuxt.config is the default for all) names a site component that wraps the body in the visual editor. It gets `item` (public fields in the active locale, media as `CmsMedia`, relations as ids, unsaved values) and `locale`, and renders the body in its default slot. Reuse it on the site page with `<CmsBlocks>` in the slot.
- Preview page: `cms.preview.path` (default `/cms/preview`, one lowercase segment under `/cms`, not `login`, `media` or an entry name). Rendered in the site's default layout, admin session required, `X-Robots-Tag: noindex, nofollow`, `X-Frame-Options: SAMEORIGIN`. It never reads the public API: the admin posts the unsaved data via `postMessage` (origin and source checked both ways; the page asks again after a reload). Block components need a single root element (the editor finds blocks by `data-cms-block`). Keep `/cms/**` out of sitemaps.

### Example

```ts
export default defineCmsConfig({
   categories: {
      id: 'categories', label: 'Categories', kind: 'collection', titleField: 'name',
      fields: { name: { label: 'Name', type: 'text', required: true } },
   },
   events: {
      id: 'events', label: 'Events', kind: 'collection', titleField: 'title', drafts: true,
      fields: {
         title: { label: 'Title', type: 'text', required: true },
         slug: { label: 'Slug', type: 'slug', from: 'title', required: true },
         description: { label: 'Description', type: 'richtext', translatable: true },
         seats: { label: 'Seats', type: 'number', integer: true },
         date: { label: 'Date', type: 'date', required: true },
         visibility: { label: 'Visibility', type: 'select', options: ['public', 'hidden'] },
         poster: { label: 'Poster', type: 'media', mediaType: ['image', 'video'] },
         category: { label: 'Category', type: 'relation', to: 'categories' },
         tags: { label: 'Tags', type: 'relation', to: 'tags', cardinality: 'many-to-many' },
         body: {
            label: 'Body', type: 'blocks',
            blocks: {
               hero: { label: 'Hero', fields: {
                  heading: { label: 'Heading', type: 'text', required: true },
                  image: { label: 'Image', type: 'media', mediaType: 'image' },
               } },
            },
         },
      },
   },
   homepage: {
      id: 'homepage', label: 'Homepage', kind: 'single',
      fields: { heroTitle: { label: 'Hero title', type: 'text', required: true, translatable: true } },
   },
})
```

## 3. Querying content

Public read-only GraphQL endpoint at `POST /api/cms/graphql`. Auto-imported composables. `useCms` and `$cmsQuery` are typed end-to-end from the query string, with no codegen step:

```ts
// one entry, query and types generated from cms.config.ts
const { data } = await useCmsSingle('homepage', { locale })
const { data } = await useCmsCollection('events', { filters, sort, limit, offset, locale })
const { data } = await useCmsPage('/about', { locale })
const { data } = await useCmsContents('news', { filters, sort, limit, offset, locale }) // publishedAt desc by default
const { data } = await useCmsContent('news', slug, { locale })                        // null when unknown, draft or scheduled

// reactive, SSR-friendly (wraps useAsyncData): use in components/pages
const { data, error, refresh } = useCms(`{ ... }`, variables?, options?)

// plain promise: use in event handlers or server-side logic
const result = await $cmsQuery(`{ ... }`, variables?)
```

`useCmsSingle` / `useCmsCollection` / `useCmsPage` need no query string. `useCmsPage` takes a typed path of the `page` entry and returns the fields of that path (shared plus its own). They select every public field of the
entry plus `id`, `updatedAt` and `createdAt`: media with all its keys, blocks with one inline
fragment per block type, relations one level deep (without the relations of the related entry).
`data` is `null` for a single and `[]` for a collection while loading and after a failure.
`sort.field` accepts only that entry's field names. Use `useCms` for a count, for a relation two
levels deep, for several entries in one request, or for a narrower selection.

`useCms` takes a third argument that forwards options to `useAsyncData`: `key` (replaces the
generated cache key), `default` (the value `data` holds before the query resolves and after it
fails), plus `server`, `lazy`, `immediate`, `deep`, `dedupe` and `watch`. The entry helpers take the
same options next to their own.

Queries started in the same tick (by any of these composables or `$cmsQuery`) go out as one batched HTTP request, and identical queries in flight share one request; keys and results are unchanged.

### Generated queries

For each **collection** `events` (GraphQL type name = PascalCase of key):

```graphql
events(filters: EventsFilters, sort: [EventsSort!], limit: Int, offset: Int, locale: String): [Events!]!
eventsById(id: ID!, locale: String): Events
eventsCount(filters: EventsFilters): Int!
```

For each **single** `homepage`:

```graphql
homepage(locale: String): Homepage
```

For each **content** entry `news`: the collection queries plus `newsBySlug(slug: String!, locale: String): News`. Without `sort` the list is ordered by `publishedAt` desc.

### Filters, sort, pagination

Filterable: `id`, `createdAt`, `updatedAt`, and every field except `json`, `blocks`, `translatable` fields, `private` fields, and `many-to-many` relations (single relations filter by the related id as a StringFilter).

Filter operators. String: `eq neq gt gte lt lte like in isNull`; Int/Float: `eq neq gt gte lt lte in isNull`; Boolean: `eq neq isNull`.

Sort: `[{ field: <fieldName>, direction: asc | desc }]` (direction defaults to `asc`).

### Media & blocks in queries

`media` fields resolve to: `{ key url type alt folder mime size width height }`, where `type` is the
enum `CmsMediaType` (`image` / `video` / `file`) and `url` is `publicBaseUrl` + "/" + `key`, `null`
only when `publicBaseUrl` is not configured.

Each `blocks` field has an interface `<Entry><Field>Block` implemented by all its block types. The
interface holds `type` plus every field that all blocks of the field declare, so a field with one
block type needs no inline fragment. Use an inline fragment for the fields of one block type; block
type names are `<Entry><Field><Block>`:

```graphql
gallery { type hidden photo { url alt } }
body { type ... on EventsBodyHero { heading image { url alt } } }
```

Block fields are always nullable in GraphQL and in `#cms-types` (`string | null`), `required` included: inside blocks `required` is an admin and save-time rule only, because stored items can predate the field. `type` and `__typename` stay non-null.

Rendering: `<CmsBlocks :blocks="item.body" />` renders each block with its `component`, the block fields as props (no `type`/`__typename`), skipping hidden blocks and blocks without a component (dev warning). It finds the component by `__typename` (selected by the generated queries); for data without it pass `entry="news" field="body"` (`field` defaults to `body`). `annotate` adds `data-cms-block` (index) and `data-cms-block-type` to each root element. Components come from a build-time map (`#cms-blocks`) of lazy imports from `#components`. Type a block component with the generated interface: `defineProps<NewsBodyTextProps>()` from `#cms-types` (name `<Entry><Field><Block>Props`); `CmsBlockProps<'news', 'body', 'text'>` is the same type for use outside `defineProps` (Vue's compiler cannot resolve the generic there).

### Example

```ts
const { data } = useCms(`query ($cat: String!) {
   homepage(locale: "it") { heroTitle }
   events(
      filters: { date: { gte: "2026-01-01" }, category: { eq: $cat } }
      sort: [{ field: date, direction: desc }]
      limit: 10
      offset: 0
   ) {
      id title date slug
      poster { url alt }
      category { id name }
      tags { id name }
   }
   eventsCount
}`, { cat: 'some-category-id' })
```

Behavior:
- Introspection is disabled outside development (`Introspection is disabled`). A query selects at most 500 fields (fixed) and nests at most `graphql.maxDepth` levels.
- `createdAt` / `updatedAt` are ISO 8601 UTC strings on every driver.
- Entries with `drafts: true` only return `published` rows (drafts are invisible to the API). Content entries also hide published items whose `publishedAt` is in the future.
- Fields with `private: true` are not in the schema at all: they cannot be selected, filtered or sorted on.
- `locale` omitted → default locale; unknown locale → error; missing translation → falls back to default locale.
- Relations resolve nested entries (localized with the parent's locale); a required many-to-one pointing to a drafted entry can still be null.
